# ADR 001: Ruvnet npm distribution through useful workflows

Status: proposed for review. Owner specification: November 8, 2026.

## Context

The November 8 inventory has 405 npm packages. Their download counts measure
registry events and cannot identify installs, users, or direct adoption.
Distribution should make packages discoverable and useful without inflating a
flagship's install or obscuring compatibility. Reconcile the frozen inventory
with the live maintainer listing at every wave; retain both cohorts.

## Decision

1. Baseline the published manifest and downloads for every npm package. Verify
   a source by GitHub owner, public visibility, a pinned commit, and an exact
   package name in the source manifest. Source repository redirects must
   resolve to a public ruvnet repository. An absent source path is a blocker
   to resolve, not permission to guess. Use a build template for generated
   platform manifests and audit aliases before proposing a migration.
2. Set npm homepage and GitHub Website to `https://ruv.io` through existing
   release and repository controls. Keep source, directory and issues links
   canonical. Use scoped keywords and repository topics tied to a verified
   feature. Document one job, supported environments, a tested command and
   expected output, and one useful next step. Preserve historic usage notes.
3. Prefer an explicit recipe or adapter for the three pilots. Add a required
   dependency only when a default path exercises it. npm optional dependencies
   can still install by default. Verify existing equivalents first.
4. Group subsequent changes by canonical owning repository and release
   template, roughly 20 to 40 manifests at a time. Publish through that
   repository's existing release train after validation; a GitHub commit or
   merged PR does not change the npm registry.

## Alternatives and tradeoffs

| Design | Benefit | Cost and risk |
| --- | --- | --- |
| Add niche packages as default dependencies | More package downloads immediately | Extra cold install time, native failures, dependency and licensing exposure, ambiguous adoption |
| Only add keywords and links | Low operational cost | Readers cannot verify that packages work together |
| Use tested recipes, with a justified dependency when needed | Preserves the default install and demonstrates value | Requires platform testing, maintenance and source verification |

The third option is selected. There is no need for a new shared runtime, paid
service, telemetry by default, or release credential. The existing registry
metrics workflow continues to own profile metrics.

## Security and provenance

Treat npm and GitHub responses as untrusted data. Collection uses fixed
provider origins, bounds response size, rejects cross-origin redirects,
validates input names and paths, and does not run package code. Public
evidence omits unresolved repository identities and outside-cohort edge names.
The source verifier does not read or write credentials; it uses the existing
GitHub connection for read-only requests and records push eligibility as
evidence, not a release grant. Verify path-level repository rules and current
head before writing. Do not use a download count to deprecate or reroute a
package.

For each new dependency edge: check cycle, duplicates, version compatibility,
native fallback, license compatibility, and lockfile advisories. Exercise the
exact documented command from a clean install. Compare package contents,
median cold install time, and install size against pinned prior versions on
supported hosts; stop the pilot if either median time or size regresses by
more than 5%. Record pass/fail/unknown by platform. Never claim that a
Linux or WASM run validates Windows or macOS.

## Promotion and rollback

The owning project reviews changes on a fresh branch and uses its normal
release workflow and controls. Verify the npm dist tag, published version,
homepage and README after release. If an added dependency regresses a path,
remove it in a patch while retaining the discovery recipe. Do not change
dist tags, bypass protected reviews, bulk publish, or deprecate to improve
an adoption number.

## Acceptance

| Requirement | Evidence or stop condition |
| --- | --- |
| Frozen coverage | All 405 IDs appear once; live changes are separately identified |
| Correct source | Exact package manifest at a pinned public source commit, or explicit blocker |
| Discovery metadata | Packed README and registry homepage read back per release |
| Safe integration | Clean execution of the exact quickstart; no unused required edge or new cycle |
| Install budget | Median time and size within 5%, or no promotion |
| Reach and adoption | Track separately; target ten external adopters in 30 days across the three pilots |

Count each external project once, using an explicit dependency, import, or
voluntary successful quickstart report. Exclude transitive lockfiles, CI
repeats and synthetic activity. Review coverage and unknowns alongside any
growth claims. Search topics are hypotheses until supported by discovery data.
