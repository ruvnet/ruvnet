# ADR 002: Grow the package graph through verified workflows

The ecosystem already has useful install paths, but a download does not show
that a feature ran. We will build the graph around jobs that users can
reproduce. This extends [ADR 001](ADR-001.md) without changing its release gates.

Run the planner against a dated npm inventory and a manifest baseline. Apply
a small dated overlay for changes relevant to the next review. Required
dependencies, optional dependencies and peers are shown separately. Reach
is a manifest graph observation, not the tree a particular npm install will
resolve, and it is never a measure of adoption. New IDs remain visible until
their manifests are observed.

For each cycle:

1. Reconcile the cohort. Pick one untested, scoped recipe from the policy. Its
   exact published versions and observable checks are fixed before running it.
2. Run the recipe from its own lockfile on a clean install. No flagship install
   changes. A failure stays in the record for revision; an unknown check stays
   incomplete. Retest a changed recipe under a new candidate revision.
3. Reconcile the receipt against the candidate, lockfile and recipe hashes.
   A pass is ready for owning project review on the recorded platform. The
   planner can then select the next candidate without retrying the passed or
   failed one. Receipts are scoped observations; their hashes do not authenticate
   who ran them and do not grant permissions.
4. Verify adoption independently: target ten distinct external repositories
   within 30 days across the pilots, counting a direct import, an exercised
   integration, or a voluntary reproducible workflow report. Keep npm events
   and adoption in separate records. Retain opt-in recipes if adoption is
   uncertain. No automatic telemetry.
5. If a required dependency is ever proposed, require current source
   ownership, a complete in-cohort graph, compatibility and licensing checks,
   a real lockfile review, supported-platform evidence, and a default
   workflow that exercises it. Apply ADR 001's 5% cold-install time and size
   gate. The planner flags a possible reverse dependency path; it does not
   prove a resolved graph has no cycle. Review and release stay with the
   owning project.

Keeping a dependency out of the default path makes rollback easy: remove the
recipe or close its proposed change. If a required edge is eventually accepted
and later regresses, remove the edge in a patch and keep discovery links.

## First candidates

| Candidate | Evidence required |
| --- | --- |
| MetaHarness Kernel and RuVector RVF | Tagged vectors persist between separate processes; an exact filter excludes the closer untagged result. |
| MetaHarness Router and Tiny Dancer | Native training and routing on a fixed fixture; same fixture decisions on TypeScript and auto selection of TypeScript in a process without Tiny Dancer. |
| Darwin and RuFANN | Equal external evaluation budget, held-out quality and a verified fallback. Compare against unscreened search before advancing. |

The first two are executable recipes. The third is the next experiment, not
a claim of improvement. Platform builds, aliases and examples remain
candidates for review when they have a concrete job; an unconnected node is
not a mandate to add a dependency. A single giant runtime, bulk required
edges and download-driven scoring were rejected because they make install
risk and causality harder to isolate.
