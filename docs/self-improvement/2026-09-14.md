# RuVnet harness improvement report · 2026-09-14

## Decision

Accepted bounded upstream-snapshot freshness and published version 0.2.2. `ruvnet changes`, `ruvnet_changes`, and `ruv://changes` now expose `current`, `stale`, or `clock-skew`, an age, a 72-hour bound, and an expiry. The MCP resource recalculates freshness on every read, including in long-running hosts. Stale or future-dated evidence produces an explicit warning. The companion remains offline, read only, and incapable of refreshing itself.

## MetaHarness loop and measured evidence

The [acceptance plan](2026-09-14-plan.json) was frozen before implementation. Nominal held-out results improved from 1/6 to 6/6; the baseline's lone pass was only the invalid-timestamp check throwing because the function did not exist. Nine test groups, manifest/schema validation, package closure, CLI, in-memory MCP and stdio MCP checks passed. MetaHarness 0.4.16 reported 6/6 hard constraints for baseline and candidate, with unchanged heuristic scores. Those scores are not proof of improvement.

Fifteen alternating baseline/candidate pairs measured 10,000 discovery calls per run and one cold CLI start per run. Median discovery p95 changed from 0.001645 ms to 0.001592 ms (-3.22%); cold CLI p95 changed from 116.461 ms to 102.034 ms (-12.39%); median resident memory increased 200,704 bytes. These clear the frozen regression gates, but the timing differences are treated as noise rather than speed gains. [Raw benchmarks](2026-09-14-benchmarks.json) preserve every sample.

The deep Ruflo 3.25.6 code and dependency scans plus npm audit reported zero findings. Manual tracked-file credential patterns returned zero files. The secret scanner reported five files and STRIDE four, so coverage is limited and the result is not a claim of complete security. Residual risks include a fixed policy that may not fit every source, hosts treating MCP annotations as enforcement, and local system clocks affecting the age calculation.

[Final candidate commit](https://github.com/ruvnet/ruvnet/commit/d5f7171e79ee4ab93ddfbf43ba3b5f953d37341f) passed [Node 22 and 24 CI](https://github.com/ruvnet/ruvnet/actions/runs/34833554431).

## Memory, WASM and GNN decision

No vector database, GNN training, persistent learning, or WASM acceleration was added or claimed. The eligible sanitized corpus remains ten projects and six change records, below the precommitted 100-record minimum. Exact lookup remains deterministic and materially simpler. A future experiment remains eligible only with a leakage-free split, at least 10 percentage points of task-success gain over exact lookup, p95 below 20 ms, and total memory below 128 MB.

## Forecast

Established results: MemForest reports lower memory-freshness latency through hierarchical temporal indexing, while ScrubJay-MEM reports improved temporal generalization from type-conditioned decay and also reports that gains reverse on fact-consolidation tasks. These are scoped preprint results, not validation of RuVnet's fixed 72-hour provenance policy. [MemForest](https://arxiv.org/abs/2605.23986) · [ScrubJay-MEM](https://arxiv.org/abs/2608.04746).

Prediction, 90 days, 80% confidence: host and memory interfaces will increasingly surface freshness or invalidation state so cached evidence cannot silently influence action beyond its useful horizon. This passes if, by 2026-12-13, at least two interoperable agent-memory protocols or major hosted connector interfaces expose freshness, expiry, or invalidation fields to clients. The MCP 2026-07-28 cache hints make this plausible but do not yet prove the prediction. [MCP release](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

The prior 30-day host-profile, 90-day provenance/cache-governance, and 180-day memory-routing forecasts have not reached their horizons. Today's change is implementation evidence for the provenance forecast, not proof of host enforcement.

## Next hypothesis

Replace the global 72-hour default with source-class-specific policy only if a held-out stale-decision dataset shows fewer wrong routing decisions with no increase in false-stale warnings. Until such a dataset exists, keep the simpler deterministic bound.
